## TARGET selection re-derived for 0.9.3.3262 (DLL 0.3.3)

The first live tamer run (GUI 0.9.12, DLL 0.3.1) showed every `TARGET` command
answering **`client build mismatch`** in the bot log, so every monster got
blocked, the tamer switched targets every tick and no `Tame` cast ever went
out. DLL 0.3.1 re-derived POS/MOVE/speed table for the 2026-11-25 client but
left the TARGET selector at the 0.9.3.3261 addresses.

Found in the **running** client (Linux PID 1818297 = Windows PID 836; the
runtime-unpacked code is not in the on-disk PE sections):

- selector prologue (unchanged signature `53 56 57 8B F2 8B F8 85 F6`)
  scanned in the live code range: **`0x005699D0`** (was `0x0057A0E4`). Its
  body checks entity `+0x33` alive, `+0x8` id, `+0xA9 != 4`, stores the
  entity at controller `+0x34` and calls the `ncif` send — same function.
- the client's own click handler at `0x0056400A` does
  `mov eax, [0x007944F0]` and calls the selector with that object, so the
  **controller global is `0x007944F0`** and it holds the controller pointer
  directly (one load; the old build used a holder and two loads). Verified:
  `[0x7944F0] = 0x252F1A08`, its vtable is in the module, `+0x34` held the
  then-selected partner entity.

DLL **0.3.3** updates `clienttarget.cpp` (`kSelector = 0x005699D0`,
`kSelectionGlobal = 0x007944F0`, `resolve_controller` one dereference). A
**game-client restart** is needed to load it.

Host 0.9.13 (applies with a GUI restart, no game restart) also stops a
build-mismatch `TARGET ... ERR` from blocking the entity or pausing combat:
it disables DLL TARGET for the session, logs the hint and falls back to
injected `ncif`. That keeps the old DLL from churning, but the client's own
selection is what makes `u_s` land, so the tamer needs DLL 0.3.3.

## The tamer (host 0.9.12)

Map/Bot → **Pet tamer** frame: **Tame monsters** toggle, **Monster vnum**
(333 = Chicken), **Tame slot** (1), **Hit until HP ≤** (25%) and a live line
with the pet slots and the run's tame count. Path **Start**/**Stop** run it;
with the toggle on the bot hunts the vnum instead of its normal combat. The
settings are saved as `tame`, `tame_vnum`, `tame_slot`, `tame_hp_pct`.

Per 50 ms tick: keep the nearest target within 15 cells → walk into range
(map A* or a 3-cell `MoveTo` on a map without data, e.g. Miniland) → Whip
until the `st` HP is at or below the limit → Tame and wait for a `msgi`
result → pre-damage the next chicken during the 15 s cooldown → repeat. It
stops on Stop, 1887 (pet slots full), 2631 ×3, three casts with no answer, or
2623.

Engine additions: `Entity.hp`/`hp_max` from `st`, `WorldState.pets` from
`sc_p`/`p_clear`, `WorldState.last_message_id`/`message_seq` from `msgi`,
and `WorldState.last_cast`/`cast_seq` from `ct`.

### First live run and the cast confirmation (host 0.9.14)

The first live tamer run (GUI 0.9.13, DLL 0.3.1 with the ncif fallback) tamed
a chicken (`tamed Chicken 3038 · pet slots 7`, `msgi 0 2614`). The second
cast at **01:40:34** — exactly 15.0 s after the first — got no answer: the
client refused to start it (its own Tame cooldown), so the bot waited out a
full cooldown and looked stuck until the user moved.

Host 0.9.14 confirms the cast: the client's started cast sends
`ct 1 <self> 3 <target> … <skill>` (the engine records `last_cast` and
`cast_seq`). A `u_s` with no `ct` within 1.5 s is a refused press — retried
after ~1 s, not counted as a failure; a started cast with no `msgi` within
4 s is a real no-answer (counted). The measured 15 s cooldown is padded to
**16 s**. The smoke now sends `ct`.

That run also proves the ncif fallback is enough for the tamer even before
DLL 0.3.3 (the Whip and Tame casts landed); the TARGET fix still matters for
the normal bot and removes the `TARGET … mismatch` lines.

**Live status:** one chicken tamed live; the cast-loop fix awaits its next
live run. The live client's pet slots were full before the run (one freed → 7
used). `gui_tame_smoke.py` covers the whole loop against a fake server.

## Pet Trainer tab and the end-to-end loop (host 0.10.0)

The tamer moved out of the Map/Bot page into its own ninth **Pet Trainer**
tab with a 50 ms state machine and per-client settings
(`~/.config/ntpl/tamer-<winpid>.json`, `NTPL_TAMER_CONFIG`). The bot config
no longer carries `tame*` fields (old files still load; the keys are
ignored). **End to end** makes the tab continue after the pet slots fill:

1. **Tame** (unchanged): Whip → Tame until the server's `msgi 0 1887`.
2. **Train** in the Miniland. The entrance is a portal on **map 1 at
   (49,133)**: the live client's `preq` there answered `at 7001 20001 …` +
   `c_map 0 20001 1` (2026-11-27 02:55:11). The summon is slot **2**
   (`u_s 2 1 <self>` → `ct … 1788`), and the spawned sparring monster is
   **vnum 1497** (`in 3 1497 1506236 …`). The pets attack with the client's
   own `suctl <map> <count> <petId> 3 <monster> …` (the manual session sent
   one pair per pet every ~1.5 s, up to 10 pairs in one packet): 02:36:59
   1502284 → 1506236, 02:36:59 1502199 → 1506236, etc. The star-rating
   message `msgi 0 2618 4 2 0 0 0` arrived 02:37:35 and 02:45:04.
3. **Extract**: slot **3** (`u_s 3 2 <petId>` → `ct … 1789`) on a pet;
   the extraction casts at 02:45:08/11/15 released the trained pets, which
   frees their slots (`p_clear` + `sc_p`), and the tab tames again.

The tab's live line shows the pet slots, chickens, tamed and extracted
counts. The E2E settings: Miniland map 20001, portal 1/49/133, summon slot 2,
sparring vnum 1497, extract slot 3, training 8 minutes (the live interval
between summoning and extraction), extract on/off. A refused extraction
(`msgi 0 2625`/`2639`, pet not maxed) trains another round, max 3.

Engine additions: `WorldState.pet_entities` from `sc_p`; the `msgi` and `ct`
handling added earlier this session. The smoke (`gui_tame_smoke.py`, run in
`bot-test`) covers tame → 1887 → summon → `suctl 20001 2 …` → shortened
training → two extracts → back to taming.

**Live status:** the packet flow is captured from the live client; the E2E
state machine itself has not run against the game yet. Open questions for
that run: the exact training time per pet (time-based for now) and whether
the client re-sends `suctl` by itself (the tab sends it every 1.5 s).
