# Handoff 2026-11-19 — multi-client bot fixes

This session ran the bot on several NosTale clients at once (FrosTale event
server, maps 1/21/46 etc.) and fixed the bugs found live. **The game clients
are the user's; nothing here restarts them.** The GUI windows were restarted
during the session on request; the user asked that this stop, so hosts must be
restarted by the user from now on.

All figures below are the verified final state: **280 host tests**, **37 bot
smokes**, **3 GUI smokes**, the native **speed-test**, and the Wine lifecycle
test pass.

## 1. Multi-client

- Each injected DLL writes its own `C:\NosTalePacketLog-<pid>.txt` (already);
  each GUI now writes its own **bot log** `~/.config/ntpl/bot-<winpid>.log`
  once it attaches (`bot.log` before attaching; `NTPL_BOT_LOG` overrides).
  The old shared `bot.log` mixed two bots' lines and looked like one bot
  switching targets.
- **Window numbering:** `Injector.exe --list` appends ` [#n]` to every
  visible game window title (`NosTale [#2]`), idempotently, numbering only
  windowed processes. The picker shows the same number, so a row and its game
  window match. `--no-tag` disables it. Verified live on five windows.

## 2. Follow mode (`follow`, `follow_player`, `follow_attack`, `follow_mirror`)

- **Follow player** (name or char id, case-insensitive): stands up, walks to
  the player with the client's own MoveTo, stops within 2 cells. While on:
  no normal combat, recovery or drawn path (the follow branch owns the tick).
  Out of sight → waits and warns **at most once per 5 s** (it used to write
  every tick, ~20×/s).
- Players who spawned before the GUI attached are **seeded from the client's
  own log** (`load_player_spawns`: `in` + later `mv`, cleared on
  `c_map`/`mapout`/`out`), so following by name can find them.
- A player **already in view when the DLL was injected** has no `in 1 <name>`
  packet in the log. The host still sees `mv 1 <charId>`, so the entity is on
  the map but nameless. The "not in sight" status now lists the map, the
  visible player names and any unnamed char ids; entering the char id in the
  Follow field follows the same entity. `gui_follow_nameless_smoke` covers
  this case.
- **Attack the same target as the player** (checkbox): reads the followed
  player's latest server `su` (`su 1 <charId> 3 <monsterId>`, 5 s TTL) and
  attacks that monster with the equipped basic skill **as soon as it is in
  range and line — also while still walking to the player**; walking resumes
  between casts. It never picks its own target and never chases.
- **Follow loot:** with the normal **Pickup** toggle on, the follower collects
  own/free drops within **10 cells of the followed player** (one `get` when
  adjacent, client MoveTo legs otherwise), then resumes following. Loot is
  checked before following movement and before the shared-target attack.
  Drops farther from the player are ignored.
- **Mirror movement & spells** (checkbox): every attached host publishes its
  own outgoing `walk`/`u_s` as JSON lines to a per-process file under
  `~/.cache/ntpl/mirror` (`NTPL_MIRROR_DIR` overrides). The follower reads
  the followed character's file, resolves the leader's `u_s` slot to a skill
  vnum and then to its own slot, and replays the movement/spell. A self/ally
  cast whose target is the followed player (or us) is retargeted to the
  follower's own char id; a third-party target is skipped. Only learned
  skills are cast; monster casts still need range and a clear line. With no
  publisher, the server's `mv`/`su` broadcasts are the fallback; the two
  copies are deduplicated. If the follower has no `ski` list (attached after
  login), it uses the leader's published `u_s` slot (same SP card),
  including slot-only events with `skill = 0`; mirrored casts follow the
  leader's cadence instead of each spell's full cooldown. The bus is plain files (atomic rename on writer
  start, per-file inode/offset tracking, 5 s event TTL) so separate GUI
  processes need no listener or port.
- Follow disables recovery by design (it would break following).

## 3. Target focus, retaliation, refusals

- **Strict focus:** the current target is kept until it dies, the client
  refuses the selection (`TARGET ... ERR`), or it leaves the 15-cell radius.
  A closer monster, another attacker or a blocked line does not steal it.
  Retaliate picks the first target and takes over after the current one dies.
- A target that **lands hits** is never dropped by refused casts. One that
  **never lands a hit** (the server cancels every attack — a client-only
  ghost) is dropped after **3 consecutive refusals**.
- Repeated refused casts pause combat **30 s**; the pause ends early after
  moving 5 cells or when a resolvable attacker hits the character (it fights
  back). A burst of `TARGET ... ERR` (3 in 10 s) pauses combat **5 s**
  instead of hopping through ghost ids.
- **In-range fight:** while the engaged monster is in skill range with a
  clear line, the bot fights in place — no drawn-path leg, no chase, no
  far-loot walk (a drop at the feet is still picked). Out of range/cover or a
  paused/refused fight: the path (or the stationary chase) moves instead.
  There is **no frozen hold** and no fixed HP heal override.

## 4. Recovery

- Trigger is **only the configured thresholds** (`Below HP %`, `Below MP %`).
  There is **no fixed 25 % rule** (an experimental 25 % override was removed
  on the user's instruction).
- **Priority: Retaliate → finish the current kill → recover.** While any mob
  hits the character the bot fights back (at any HP). Then it finishes the
  target it was already fighting. Only then does it sit.
- `FINISH_KILL_GRACE_S = 12`: a target the bot has not attacked for 12 s no
  longer defers recovery (this was the “recovery only works after
  Stop/Start” bug: a stale `fight_target_id` from an unreported kill).
- `recovery_pending` is set as soon as a threshold is crossed. From then on
  the bot **cancels route and loot walks (also in flight)** and **never picks
  a new monster**; only retaliation and finishing the current target are
  allowed, then it sits.
- Being hit still aborts/skips recovery while not finished (old “fight back”
  behavior); the finish-kill deferral applies only to a recently attacked
  target.
- `REST_RETRY_S = 5`: `rest` is a toggle and its confirmation lags with many
  clients; re-sending too early stood the character back up (sit/stand loop).
  The DLL's `MOVE: character is sitting (stand up first)` is trusted: the
  refused leg is cancelled and the bot stands immediately.
- Recovery waits for **full** HP/MP, then stands and resumes.

## 5. Pathing and route editing

- **Start plans from the character's current position** to the nearest
  remaining leg; the saved Draw-path start point is **never walked to**.
  Stop/Start (or a manual move) resumes the route instead of re-treading it;
  standing on the last waypoint re-runs the route.
- The **drawn preview always keeps the whole route**; clicks add/remove
  waypoints and never shrink or reset it. A route without a start point just
  gains a waypoint (it used to clear the whole path). The preview in
  `path_cells` is separate from the execution path planned at Start
  (`_apply_execution_path`).
- Clicking while the bot runs no longer rewinds `path_index`.
- **Interruptions:** a server `tp` for the character to a cell the bot did not
  command (manual move or correction) clears the pending leg and re-plans
  from there (0.5 s throttle). Client `walk` sends are deliberately **not**
  used for this — the client's own path need not carry the commanded cell,
  and comparing it caused false "walk interrupted" replans.
- Starting while seated: if the first MOVE reveals the character is sitting,
  the leg is cancelled and the bot stands before the next leg.

## 6. Performance — the “Not Responding” fix

- A client's DLL log had reached **96.5 MB / 4.6 M lines**. Every GUI attach
  re-scanned the whole file **8 times** (spawns, player seeding, names,
  skills, last position, gates, portals, time-spaces) on the GTK main thread
  — minutes of frozen window. Re-attaching repeated it.
- The host backfill now reads only the **last 8 MB** of the log; the login
  `ski` skill list is read from the **first 8 MB**. On the real 96.5 MB file
  all 8 parsers finish in **~1.1 s total**.
- The DLL now caps its log at **16 MB** and truncates in place with a
  `log truncated` status line. This needs a client restart/reinjection to
  take effect in a running client; the host fix alone removes the freeze with
  the existing files.

## 8. Operational notes

- The GUI is non-unique: one window per game client, per-client attach locks
  under `~/.cache/ntpl`. Restart the GUI windows to load host changes.
- The injector refuses a second `PacketLogger*.dll` in the same process
  (two loggers crash the client) — restart the game client after a `QUIT`.
- Stale `ntpl-<pid>.port` files are ignored when nothing listens on the port.
- The Gameforge client itself (its Wine prefix, font/NosMall fixes, account
  "Running" states) is documented in `~/games/gameforge/CLAUDE.md`, not here.

## 9. Known limitations

- Follow reports “not in sight” if the player is on another map or spawned
  before the DLL was injected (no `in`/`mv` in this client's log). Move the
  followed character once or re-enter the area; both characters must be on
  the same map.
- A killed monster whose `st` was never received can linger in the world
  state; it is removed on a `TARGET ... ERR` or after 3 consecutive refused
  casts, but may cause a short burst first.
- Large drawn routes (80+ waypoints): the preview re-plans every leg on each
  click/Start, which can take seconds and briefly stall the UI. Lazy planning
  is not implemented.
- The bot is for the account owner's own client; Gameforge prohibits
  automation and the account risk is the owner's.

## 12. Speed boost (2026-11-20)

**Speed +** (**Malicious** tab, 0–50, default 0) adds a flat bonus (+1, +2,
+3...) to the character's walking speed client-side — the idea Phoenix Bot
lists as "speed hack" and marks high ban risk.

- **Current mechanism (Phoenix-style clamp):** the DLL reads the server's
  `cond 1 <charId> … <speed>` to learn the base (or reads the player entity's
  current speed if no cond has arrived), calls the client's own entity speed
  setter (`0x00492938`) on the local player actor (`[player+0x20]+0xAA`) so
  the client moves faster, and **clamps the outgoing `walk` speed back to the
  server's cond value**. The server sees a normal walk field; the `cond`
  packet is not modified. A 25 ms worker watchdog re-applies the entity value
  because the client's own cond handler resets it on every packet. The setter
  caps at 59.
- **The upward packet rewriting caused the kick:** earlier builds rewrote the
  `cond` speed and the outgoing `walk` speed **above** the server's value. On
  the live server the client moved at 12/14 while the server simulated 16/18;
  it sent `tp` corrections every few seconds and kicked the account
  (13:39–13:40; base 14 + 4 → 18). Those upward rewrites were removed; the
  current build only clamps the walk field **down** to the server's own cond.
- **Safety (0.2.5):** the requested value applies **immediately**; the 8 s
  +1 probe was removed once the walk clamp made it unnecessary. At the first
  `tp 1 <self>` while a boost is active, the DLL settles at **+1** (or turns
  off if the correction hits +1) and sends `STATUS|SPEED TUNED 1` /
  `STATUS|SPEED CORRECTED`; the GUI shows the limit and sets the spin
  silently. The clamp is what makes +10 usable; the probe was only needed
  for the un-clamped builds.
- **Host control:** `SPEED|<add>` (clamped 0–59) is sent on attach, when the
  spin changes, and `SPEED|0` on shutdown; the DLL also stops on disconnect.
  `speed_boost` in the bot JSON (default 0). The boost applies while the GUI
  is attached, not only while the bot runs.
- **Live verification (2026-11-20 14:45, client PID 1948, base cond 11):**
  the walk clamp works (0.2.4 had the probe; 0.2.5 applies immediately).
  `speed +3` logged `testing +1` (actor 11→12); the probe passed and applied
  +3 (actor 12→14); every outgoing `walk` was 11
  (the server's cond). Continuous movement produced **no `tp 1 7125`** —
  the client moves at 14 while the server sees 11. The user then changed
  maps; the next request reset the actor. This is the Phoenix-style hack:
  local speed is faster, the server sees the normal walk field.
- **Earlier failures:** un-clamped builds sent walk 12/13/16 against cond
  11/12 and were corrected within 4–5 s (13:39, 14:24, 14:26). The clamp
  fixes that. The forced second-DLL injection at 14:32 crashed the client;
  the injector now refuses `--force` while the old port file exists.
- **Version visibility:** the host is `0.2.6` (DLL `0.2.5`); the window
  title shows `NosTale Packet Logger 0.2.6 — <client> · DLL <version>` and the
  client picker reads each DLL version from its `NosTalePacketLog-<pid>.txt`
  start line, so a stale client is obvious before attaching.
- **Reload without a client restart:** the old DLL's `QUIT` removes its
  hooks and leaves the module inert. `Injector.exe --pid <pid> --dll
  <new-name>.dll --force` then loads the new DLL. `--force` is only for after
  QUIT and **refuses while `C:\ntpl-<pid>.port` still exists** (a second
  live logger crashes the game; this happened at 14:32 when the old GUI held
  the port and the forced second DLL took down the client). This was used for
  the 14:24 test with `ntpl024b.dll`.
- **Reset fix:** `client_speed_set(..., force=true)` lowers the entity when
  the boost is turned off or the server settles on a lower value; without it
  an idle client stayed at the last boosted speed (no cond to reset it) and
  the next attempt was corrected immediately.
- **Tests:** `make -C linux speed-test` (cond parsing, flat bonus, cap) and
  `gui_speed_boost_smoke.py` (GUI control, including the correction reset).
  Full counts: 280 host, 37 bot, 3 GUI smokes.
